## Résumé exécutif

Soundy est une application sociale musicale techniquement ambitieuse, avec un backend Node.js/Express solide, une stack TypeScript cohérente, et des fonctionnalités différenciantes (globe 3D, salons synchronisés Spotify/YouTube, lives géolocalisés). La base de code est bien organisée et dispose d'une couverture de tests unitaires correcte sur les modules clés.

**Les points forts** : architecture de sécurité soignée (JWT + 2FA TOTP chiffré AES-256-GCM + WebAuthn + OAuth), chiffrement des tokens OAuth au repos, gestion fine de la confidentialité géographique, rate limiting présent sur les routes sensibles, infrastructure de backup à trois couches.

**Les risques majeurs** : (1) le store entier en mémoire RAM avec scan O(n) sur toutes les requêtes géographiques — bottleneck critique à 100+ users ; (2) Spotify encore en mode développement (quota 25 users), bloquant tout lancement public ; (3) les fichiers audio (compositions) stockés sur le VPS filesystem sans objet storage, RPO 7 jours ; (4) pas de rate limit sur `/api/geo/nearby` appelé toutes les 30 secondes ; (5) IP whitelist Caddy hardcodée pour une seule box (195.36.171.84/32) qui contourne la basic auth.

**Score composite** : Fonctionnel 16/20 · UX 13/20 · Performance 12/20 · Sécurité 15/20 · Code Quality 15/20.

## 1. Fonctionnel

### ✅ Fonctionne bien

- **Authentification complète** : login/register, email verification, forgot/reset password, 2FA TOTP + backup codes (bcrypt), WebAuthn/passkeys, OAuth Google/Spotify/YouTube/Instagram — flux complets et cohérents
- **Salons musicaux** : création, join, playback Spotify Connect + YouTube iframe, file d'attente, propositions de morceaux, VIP modérateur, chat, 2h max enforced côté serveur
- **Lives** : trois modes (LiveKit WebRTC, Cloudflare Stream RTMP, mesh peer-to-peer), 8h max, ICE servers TURN, bans, dons live
- **Matching (hearts)** : triple gate — âge ≥ 18, statut "célibataire", compte actif ; mutual heart → déblocage DM — logique propre dans `canSendHeart.ts`
- **Feed / Stories / Reels** : création, likes, commentaires, partages, vues persistés en PG
- **Géolocalisation** : debounce 4 secondes, floutage des coordonnées, mode ville seule, ghost mode
- **Admin panel** : gestion comptes, contenu, sponsors, signalements, monitoring VPS, syslog
- **Donations / Abonnements** : Stripe Connect, simulation mode, âge gate 18+
- **Compositions** : upload audio (mp3/wav/m4a/ogg/webm/flac ≤ 30 Mo), stockage filesystem + persistance PG
- **Notifications** : WebSocket Socket.io + fallback polling, push web (VAPID)
- **RGPD** : export données (`/me/export`), suppression en cascade, mentions légales publiques

### ⚠️ Points d'attention

- **Salon expiration** : le scheduler vérifie toutes les 5 min — un salon peut rester actif jusqu'à 5 minutes après l'expiration avant suppression (fenêtre de grace non documentée)
- **Geo `/nearby` sans rate limit** : appelé côté client toutes les 30 secondes depuis `HomePage.tsx` (`GEO_REFRESH_INTERVAL_MS = 30_000`). Avec 100 users concurrents = 3.3 req/sec sur une route O(n³) (scan users + salons + lives)
- **Vérification email non obligatoire en production** : `SKIP_EMAIL_VERIFICATION=true` dans `.env` bypasse complètement la vérification — risque si accidentellement activé en prod
- **Email enumeration** : `/register` retourne HTTP 409 "Utilisateur déjà existant" si l'email existe — mineur mais détectable
- **User ID non-opaque** : `user_${Date.now()}_${random5chars}` — le timestamp est prédictible
- **Compte OAuth sans termsVersion** : les nouveaux users OAuth n'ont pas de `acceptedTermsVersion` stockée (champ absent dans `findOrCreateOAuthUser`)
- **Salon listeners count** : le champ `listenersCount` n'est pas décrémenté en temps réel à la déconnexion socket — compteur dérivable mais potentiellement désynchronisé

### 🔴 Bugs critiques

**BUG-01** — `locationPrivacy.ts` : `resolveCityCoordinates` ne couvre que 18 villes hardcodées. Tout utilisateur hors de cette liste reçoit des coordonnées pseudo-aléatoires centrées sur Paris (hash de string → lat/lon Paris ± 0.04°). Un utilisateur de Lyon 7ème se retrouve géolocalisé en dehors de Lyon. Impact : affichage carte incorrect, matching géo faux.

```
// backend/src/lib/locationPrivacy.ts:41-51
export function resolveCityCoordinates(city: string): [number, number] {
  const normalized = city.trim().toLowerCase();
  for (const entry of CITY_LOOKUP) { if (entry.match(normalized)) return [entry.lat, entry.lon]; }
  // Fallback: hash → Paris ± tiny offset
  let hash = 0; ...
  const lat = 48.8566 + ((hash % 1000) / 1000 - 0.5) * 0.08; // toujours autour de Paris!
```

**BUG-02** — `auth.ts` : `PROFILE_CACHE_MAX_SIZE = 1000` avec `pruneProfileCache()` appelé seulement quand `size >= 1000`. En production avec beaucoup d'utilisateurs (viewer × target combinations), la Map peut croître sans bound — potentielle fuite mémoire. Le TTL est 30 secondes mais la Map n'est pas bornée en temps normal, seulement à 1000 entrées.

**BUG-03** — `storeCore.ts` + `pgStore.ts` : la sauvegarde périodique (persist loop) sérialise l'ensemble du store en JSON, incluant les messages DM, chats salons, etc. Avec des milliers d'utilisateurs, ce blob JSON peut dépasser les limites de la colonne `store` (JSONB PostgreSQL max ~250 Mo en pratique). Pas de chunking.

**BUG-04** — `dm.ts` : le `_legacyAcceptedCache` (Set en mémoire) est partagé globalement et invalité via `invalidateLegacyAcceptedCache()`. Si deux requêtes DM arrivent quasi simultanément (race condition), le cache peut être lu avant d'être reconstruit — le Set null retourne `false`, refusant un DM accepté.

## 3. Performance

### État actuel (load test du 19/06/2026)

Le load test Artillery (`docs/loadtest.yml`) montre :
- **p99 latence HTTP ≈ 20-27ms** — excellent pour endpoints légers (health, geo, auth)
- **Charge maximale testée : ~12 req/sec** — très faible, non représentatif de la prod
- Aucun échec (`vusers.failed: 0`) — stable à faible charge

### Bottlenecks identifiés

**PERF-01 — `getNearbyPeople` O(n) sur tous les users** (`backend/src/lib/nearbyPeople.ts:218`):
```typescript
for (const u of db.users.values()) { // ← scan complet
  const pos = getUserPublicCoords(u, viewerId);
  if (!pos) continue;
  const d = getDistanceKm(lat, lon, pos.lat, pos.lon);
  if (withinRadius(d)) upsert(u, d);
}
```
Avec 1 000 users : ~1ms. Avec 10 000 users : ~10ms. Avec 100 000 users : ~100ms **par requête**, appelée toutes les 30s par chaque user connecté. À 500 users connectés = 16 req/sec sur ce scan.

**PERF-02 — `/api/geo/nearby` sans pagination ni rate limit** : retourne tous les salons, lives, personnes dans le rayon. Avec `distanceFilter=false` (option activée), `resolveNearbyRadiusKm` retourne `null` → **aucune limite de distance** → retourne potentiellement tous les objets en base.

**PERF-03 — Store JSON blob monolithique** : `pgStore.ts` sérialise la totalité de la DB en mémoire en un seul JSON pour la persistance périodique. Avec 1 000 users ayant chacun des DMs, reels, feed posts → blob JSON de plusieurs dizaines de Mo. Durée de la sérialisation + écriture PG peut prendre plusieurs secondes, bloquant le garbage collector.

**PERF-04 — Profile photos base64 en RAM** : chaque photo est stockée en base64 dans le champ `profilePhotos[]` du User (jusqu'à 6 × 2 MB = 12 MB en base64 par user). En RAM pour tous les users actifs. 1 000 users avec photos = potentiellement 12 GB RAM — impossble sur DEV1-S (2GB total).

**PERF-05 — Globe Three.js : 5 000 markers max desktop** (`GlobeView.tsx:60-61`):
```typescript
const GLOBE_PEOPLE_CAP = IS_LOW_POWER_DEVICE ? 800 : 5000;
```
5 000 instanciations Three.js avec re-render à chaque mise à jour. Sans memoization agressive (bien implémentée via `globePointsEqual`), acceptable jusqu'à ~500-1000 markers réels.

**PERF-06 — Tile cache local : 500 MB max** (`tileCacheEviction.ts`) — bon, tiles CARTO proxiées localement, TTL et eviction correctement gérés.

**PERF-07 — Absence de Redis/cache distribué** : le profile cache (in-memory, 1000 entries, TTL 30s) ne survit pas à un redémarrage et n'est pas partageable si on scale.

### Estimations de capacité

| Scenario | Users connectés | Charge /geo/nearby | RAM Node.js | Verdict |
|----------|----------------|-------------------|-------------|---------|
| MVP | 10 | ~0.3 req/s | <50 MB | ✅ OK |
| Croissance | 100 | ~3 req/s | ~200 MB | ✅ OK |
| Stress | 500 | ~16 req/s | ~1 GB | ⚠️ Limite VPS |
| Scale | 1 000 | ~33 req/s | >2 GB | 🔴 OOM crash |

## 4. Sécurité

### OWASP Top 10 — Analyse

**A01 — Broken Access Control** : ⚠️ MOYEN
- Les routes admin (`/api/access/admin/*`) sont protégées par `authenticateJWT` + flag `isAdmin` en base ✓
- Le `authenticateJWT` middleware vérifie `canUserUseApp()` (status actif/bloqué) ✓
- Pas de CSRF explicite sur les mutations (mitigation : SameSite cookies absents car JWT header, pas cookie — réduit le risque)
- **Risque** : `/api/config` exposé sans auth retourne `APP_ENV` — information disclosure mineur

**A02 — Cryptographic Failures** : ✅ BON
- JWT signé avec secret HMAC-SHA256, durée 7j (remember me) ou 24h
- Passwords bcrypt salt factor 10 ✓
- Tokens OAuth chiffrés AES-256-GCM au repos (`tokenEncryption.ts`) ✓
- TOTP secrets chiffrés AES-256-GCM (`twoFactor.ts`) ✓
- `ENCRYPTION_KEY` distinct de `JWT_SECRET` requis en production ✓
- **Risque mineur** : le JWT secret est récupéré via `getJwtSecret()` — si non défini en prod, la fonction lève une exception au démarrage (correct)

**A03 — Injection** : ✅ BON
- Toutes les requêtes PG utilisent des paramètres préparés (`$1, $2...`) ✓
- Pas de construction de query SQL dynamique détectée
- **Risque potentiel** : `bio`, `interests`, `city` reçoivent `.slice(0, N)` mais pas de sanitization XSS explicite — dépend du frontend pour l'échappement

**A04 — Insecure Design** : ⚠️ MOYEN
- `user_${Date.now()}_${random5chars}` — timestamp prévisible dans l'ID
- Reset token et verification token stockés en clair dans le User object (non hashés) — si la DB est compromise, les tokens de reset valides sont exposés

**A05 — Security Misconfiguration** : ⚠️ MOYEN
- **Caddy IP whitelist** : `195.36.171.84/32` bypass la basic auth complètement. Si cette IP change (box FAI → IP dynamique), l'adresse hardcodée ne correspond plus, mais aucun risque de sécurité additionnel (l'IP n'a pas accès à plus que n'importe quel autre user authentifié par basic auth)
- **HSTS désactivé** (`strictTransportSecurity: false` dans Helmet) par design (accès IP HTTP) — acceptable pour la transition, à activer post-stabilisation
- **CSP broad** : `img-src: https:` et `connect-src: https: http:` très larges — permettent des requêtes vers n'importe quel domaine tiers
- **`/health` exposé sans auth** : révèle `APP_ENV`, état DB — information disclosure pour un attaquant
- **VPS CORS_ORIGIN** : `.env.production.example` montre `CORS_ORIGIN=http://51.159.164.100` (HTTP, non HTTPS) — à corriger

**A06 — Vulnerable Components** : ⚠️ ATTENTION
- Dépendances non auditées dans ce rapport — `npm audit` recommandé
- `otplib` pour TOTP, `jsonwebtoken`, `bcryptjs`, `qrcode` — packages établis

**A07 — Authentication Failures** : ✅ BON (avec réserves)
- Rate limit sur login/register : **100 req/15 min par IP** — assez permissif pour un brute-force distribué (100 passwords en 15 min sans blocage progressif ni lockout)
- 2FA validate : 5 tentatives/15 min ✓
- OAuth CSRF state (32 bytes random, TTL 10 min) ✓
- Temp token 2FA expirant en 5 min ✓
- **Risque** : pas de lockout progressif sur le login (après N échecs, délai croissant)
- **Risque** : pas de détection de connexion depuis nouvelle IP/pays

**A08 — Software and Data Integrity** : ✅ BON
- Stripe webhook signature vérifiée (`express.raw` + `stripe.webhooks.constructEvent`) ✓
- Deploy via git + PS1 script — pas de pipeline CI/CD automatisée avec validation

**A09 — Security Logging** : ⚠️ PARTIEL
- `trackEvent('user_login')` en analytics ✓
- Monitoring alerts (disk, RAM, CPU, uncaught exceptions) ✓
- Pas de logging des échecs d'authentification avec IP
- Pas de SIEM ou log aggregation externe

**A10 — SSRF** : ⚠️ MOYEN
- Le geocoder fait des requêtes HTTP vers `geo.api.gouv.fr` et `nominatim.openstreetmap.org` — les paramètres sont construits avec `URLSearchParams` (sûr) ✓
- YouTube et Spotify : fetch vers leurs APIs avec tokens contrôlés ✓
- **Risque** : tile proxy (`/tiles/{z}/{x}/{y}`) fetch depuis CARTO — URL construite côté serveur avec paramètres validés (z, x, y entiers) ✓

### Failles critiques identifiées

**SEC-01 — Reset tokens et verification tokens stockés en clair dans le User object**
```typescript
// auth.ts:649-653
user.resetToken = resetToken;          // clair en mémoire et en PG JSONB
user.resetTokenExpiry = resetTokenExpiry;
```
Si la DB PostgreSQL est compromise, tous les tokens de reset actifs sont utilisables immédiatement. Recommandation : hasher avec SHA-256 avant stockage.

**SEC-02 — `alertNotifier.ts` : email admin hardcodé dans le code source**
```typescript
// alertNotifier.ts:41
recipients.add('admin@getsoundy.com'); // ← toujours inclus, même si SMTP_ADMIN_EMAIL change
```
L'adresse email de l'admin est hardcodée. Retirer ce hardcode, utiliser uniquement les variables d'environnement.

**SEC-03 — File upload compositions : pas de vérification du magic bytes**
Le filtre `COMPOSITION_AUDIO_DATA_RE` valide uniquement le MIME type déclaré dans la data URL, pas le contenu réel. Un attaquant peut envoyer un fichier malveillant avec un header audio valide. Ajouter une vérification des premiers bytes (magic numbers) du buffer.

**SEC-04 — Nominatim rate limit côté serveur partagé**
`lastNominatimAt` est une variable globale. Plusieurs requêtes simultanees peuvent dépasser la politique 1 req/sec de Nominatim si les requêtes arrivent en burst — risque de ban IP de Nominatim.

## 5. Code Quality

### Points forts

- **TypeScript strict** : modèles bien typés, interfaces exportées
- **Séparation des responsabilités** : routes → `lib/` → `models/schema.ts`, bonne granularité
- **Tests unitaires** présents sur les modules critiques : `ageGates.test.ts`, `donations.test.ts`, `canSendHeart` (via les mocks), `locationPrivacy.test.ts`, `subscriptions.test.ts`, `chatRateLimit.test.ts`, `salonPlaybackOps.test.ts`
- **Error handling** : try/catch systématique sur les opérations async, réponses HTTP cohérentes
- **Memoization WebGL** : accesseurs Three.js stables au niveau module pour éviter les re-renders inutiles

### Anti-patterns identifiés

**CODE-01 — Store global mutable en RAM** : `db` dans `models/schema.ts` est un singleton global partagé par tous les handlers Express. Pas thread-safe (Node.js est single-thread, donc ça fonctionne, mais limite scalabilité). Chaque scan `[...db.users.values()]` crée un tableau intermédiaire inutile.

**CODE-02 — O(n) lookups systématiques** : au lieu d'indexes, tout passe par `.find()` ou `.values()` scan. Exemples :
```typescript
// auth.ts:97 — O(n) sur chaque register
const exists = [...db.users.values()].some((u) => u.email === email || u.username === username);
// auth.ts:177 — O(n) sur chaque login
const user = [...db.users.values()].find((u) => u.email === email);
```
Avec 10 000 users, chaque login parcourt 10 000 objets.

**CODE-03 — Duplications routes admin** : les vérifications `isAdmin` sont répétées dans plusieurs fichiers admin (`adminContent.ts`, `adminSponsors.ts`, `adminCloudflare.ts`) sans middleware centralisé.

**CODE-04 — Composition sans limite de count par user** : `createUserComposition` n'impose pas de limite du nombre de compositions par user. Un user peut en créer des milliers, saturant le disque VPS.

**CODE-05 — `resolveListeningPlatform` approximatif** (`nearbyPeople.ts:90-106`) : retourne toujours `connected[0]` si plusieurs plateformes connectées — non déterministe, peut afficher la mauvaise plateforme.

**CODE-06 — `locationPrivacy.ts` fragile** : la liste hardcodée de villes (`CITY_LOOKUP`) ne couvre pas les villes françaises de taille moyenne (Nantes, Strasbourg, Bordeaux, Toulouse, Rennes...). Les users de ces villes sont géolocalisés à Paris.

**CODE-07 — `pgStore.ts` : `assertSafeUserSnapshot` silencieux** : si la sauvegarde échoue (snapshot invalide), l'erreur est loggée mais la persist loop continue — données en production non sauvegardées sans alerte proactive.

## Tests spécifiques

### Synchronisation Spotify

- **Quota** : En mode développement, limite stricte de **25 utilisateurs whitlistés**. La demande Extended Quota Mode n'est pas encore soumise. **Bloquant pour tout lancement public.**
- **OAuth flow** : Correct — CSRF state 32 bytes, TTL 10 min, scopes explicites (`SPOTIFY_SCOPES`), refresh token implémenté
- **Token refresh** : `TOKEN_EXPIRY_BUFFER_MS = 60_000` — rafraîchissement 1 min avant expiration ✓
- **Spotify Connect** : requiert un appareil actif chez l'hôte. Sans appareil, `playSpotifyTrackNow` échoue avec `SpotifyPlaybackError` — message propagé mais UX confuse
- **Rate limits Spotify** : 429 retournés au client, pas de retry exponential backoff côté backend
- **Branding** : `PoweredBySpotify.tsx` présent dans les composants salon ✓

### Synchronisation YouTube

- **OAuth** : `youtube.readonly` scope seulement — conforme aux CGU YouTube ✓
- **Fallback** : `youtubeDataApiKey()` — si API key configurée, recherche possible sans OAuth hôte ✓
- **Cache recherche** : TTL 1 heure côté backend (`ytSearchCache`) — évite dépassement quota YouTube ✓
- **Playlist** : `resolvePlaylistVideos` — requiert OAuth YouTube hôte pour playlists privées
- **Compliance DRM** : YouTube ne permet pas le re-streaming de l'audio via API — Soundy joue les vidéos dans un iframe sans re-encoder l'audio ✓ (conforme)

### Salons musicaux

- **Création** : OK, persistance immédiate en PG (`upsertSalonToPgAsync`)
- **Join** : vérification accès (`canJoinSalon`) — salon privé/invite/public ✓
- **Listeners count** : champ `listenersCount` mis à jour par Socket.io events — potentiellement désynchronisé si crash
- **Expiration** : scheduler 5 min — fenêtre d'expiration ±5 min acceptable
- **Chat history** : purge à `MAX_CHAT_MESSAGES_PER_ROOM = 500` ✓
- **Propositions** : vote de morceaux, approbation hôte/VIP ✓

### Matching

- **Age gate** : `HEART_MIN_AGE = 18` (`CREATOR_MONETIZATION_MIN_AGE`) — vérifié sur sender ET receiver ✓
- **Célibataire gate** : sender ne doit pas être `en_couple`, receiver doit être `celibataire` — asymétrique intentionnellement ✓
- **Mutual hearts** : `findMatch` dans `matches.ts` — détection correcte
- **DM après match** : déclenche création de conversation DM ✓
- **Edge case** : si un user change son statut de `celibataire` à `en_couple` après avoir envoyé un cœur, les cœurs existants restent valides (pas de rétroaction)

### Géolocalisation

- **Précision** : `blurCoordinate` ajoute du bruit gaussien (~300m) — respects privacy ✓
- **Fallback si refusé** : si GPS refusé, l'app utilise la ville du profil → `resolveCityCoordinates` — **problématique pour les villes non listées** (BUG-01)
- **Privacy levels** : `precise` (GPS flou) vs `city` (centroïde ville) ✓
- **Ghost mode** : `isGhostMode: true` → invisible de la carte ✓

### Notifications temps réel

- **WebSocket** : Socket.io avec rooms `user_${id}`, `salon_${id}`, `live_${id}` ✓
- **Push Web** : VAPID push (`webPush.ts`, `pgPushSubscriptions.ts`) ✓
- **Fallback polling** : non implémenté pour les notifications en-app — si socket déconnecté, les notifications peuvent être manquées jusqu'à reconnexion
- **Unread DM count** : émis via socket `dm_unread` ✓

### Performance à l'échelle

- **10 users** : ✅ Aucun problème
- **100 users** : ✅ OK, charge geo/nearby ~3 req/s acceptable
- **1 000 users** : ⚠️ `getNearbyPeople` ~30ms/req + 33 req/s = problème. RAM Node ~800MB
- **10 000 users** : 🔴 OOM certain (photos base64 seules = >10 GB RAM possible). Store JSON write timeout. getNearbyPeople ~300ms/req

### Risques juridiques Spotify/YouTube

**Spotify** :
- Utilisation des scopes `user-modify-playback-state` pour contrôler Spotify Connect ✓ (conforme Developer Policy)
- Pas de streaming audio dans le navigateur via Web Playback SDK ✓ (intentionnel, conforme)
- Affichage "Powered by Spotify" requis — présent ✓
- **CRITIQUE** : Extended Quota Mode non obtenu — seuls 25 users peuvent connecter Spotify

**YouTube** :
- iframe embed avec `youtube-nocookie.com` ✓
- `youtube.readonly` scope — pas de modification de données user ✓
- Affichage logo YouTube requis sur les recherches — présence à vérifier dans `SalonYouTubeSearch.tsx`
- Quota YouTube Data API v3 : 10 000 unités/jour par défaut — recherche = 100 unités, surveillance nécessaire
