MODIF 482 — Suppression verify-access à la sélection playlist (create salon)
================================================================================
Date : 2026-06-13

## Symptôme
Dans CreateSalonModal, choisir une playlist dans la liste déclenche une erreur
(`spotify_playlist_forbidden` ou message reconnect) alors que la même playlist
apparaît dans `/me/playlists`. Le collage d'URL fonctionne mieux car le flux diffère.

## Cause
MODIF 481 a ajouté `verifyPlaylistAccess` (POST verify-access → `/items`) **au clic
sur la liste** avant d'enregistrer la sélection. Playlists déjà listées par l'API
hôte peuvent échouer ce pré-vol prématuré ; l'utilisateur ne voit jamais la sélection.

## Correctif
### Frontend
- `CreateSalonSpotifyPlaylistPicker` : sélection liste/URL → stocke id/titre sans verify.
- Vérification conservée uniquement à la **création du salon** (`CreateSalonModal.submit`
  → verify-access puis createSalon + load-playlist), comme `SalonSpotifyPlaylist` qui
  verify au clic « Lancer » et non au changement de `<select>`.

## Filtre retiré
- verify-access **on select** dans CreateSalonSpotifyPlaylistPicker (pickFromList, pickFromUrl).

## Nouveau flux sélection
1. GET `/platforms/spotify/playlists` → liste complète `/me/playlists` (sans filtre extra).
2. Choix liste ou URL → `onChange({ playlistId|playlistUrl, title })` immédiat.
3. Submit create salon → verify-access (backend `/items` + fallback) → createSalon → load-playlist.

## Fichiers
- app/src/components/CreateSalonSpotifyPlaylistPicker.tsx
- modification.txt

  cd app && npm run build          ✓

MODIF 481 — Fix 403 playlist tracks → /items + fallback metadata
================================================================================
Date : 2026-06-13

## Symptôme (persistant après MODIF 480 déployé SHA 6ab16fc0)
Création salon Spotify avec playlist : toast
« Accès à la playlist refusé — choisissez une playlist de votre bibliothèque ou reconnectez Spotify. »
(code `spotify_playlist_forbidden`).

- `verifySpotifyPlaylistTrackAccess` et `resolveSpotifyPlaylistTracks` partagent `openSpotifyPlaylistItemsSession`.

### Frontend
- `CreateSalonSpotifyPlaylistPicker` : verify-access au clic liste (comme URL) avant sélection.

Fin MODIF 481 - 2026-06-13
================================================================================

Date : 2026-06-13

## Symptôme (persistant après MODIF 479 déployé SHA 8f14a91b)
Après déconnexion + reconnexion Spotify, onglet playlist CreateSalonModal affiche
toujours « Reconnectez Spotify pour autoriser l'accès aux playlists » + bouton
Reconnecter — la reconnexion ne corrige rien.

## Cause racine (preuve prod VPS 51.159.164.100, user user_1781017431039_0npao)
1. **Boucle invalidate → gate DB** : probe `/playlists/{id}/tracks` renvoie 403 Forbidden
   alors que `oauthScopes` contient déjà `playlist-read-private` + `playlist-read-collaborative`.
   `invalidateStoredSpotifyOAuthScopes(probe:tracks_403)` efface les scopes.
2. **Gate DB bloque le live** : `probeSpotifyHostSession` retournait `spotify_scope_missing`
   dès `oauthScopes` vide, **sans** appeler `/me/playlists` → reconnexion inutile.
3. **Track probe trop strict pour la session** : échec tracks sur la 1ère playlist (ex.
   podcast/région) invalidait toute la session alors que `/me/playlists` OK.
4. **OAuth scope absent** : si Spotify omet `scope` dans la réponse token, `oauthScopes`
   restait undefined après reconnect.

## Correctif
### Backend
- `probeSpotifyHostSession` : **plus de pré-vérification DB** ; validation live via
  `/me` + `/me/playlists` uniquement (plus de track probe session).
- `syncStoredScopesAfterListProbeOk` : persiste `SPOTIFY_SCOPES` si list OK et DB vide.
- `resolveSpotifyOAuthScopesAfterConnect` : si token sans scope mais `/me/playlists` OK,
  persiste les scopes demandés.
- `persistStoredSpotifyOAuthScopes` : helper explicite ; invalidation limitée aux 403
  **liste** avec message scope explicite (plus sur tracks).
- `throwSpotifyPlaylistApiError` : 403 bare sur **tracks** → `spotify_playlist_forbidden`
  (pas scope_missing + pas invalidate).
- Routes OAuth : `forceConsent` auto si `userNeedsSpotifyScopeReconnect` ; POST connect
  Spotify toujours `show_dialog=true`.

### Frontend
- `PlatformConnectCard` : connexion Spotify toujours avec `reconnect: true` (show_dialog).

Fin MODIF 480 - 2026-06-13
================================================================================

Date : 2026-06-13

## Symptôme (persistant après MODIF 478)
Création salon Spotify avec playlist : toast « Forbidden » ou « Session expirée »
alors que /me/playlists listait les playlists. Logs prod :
  [spotify-playlist] API error { status: 403, detail: 'Forbidden', context: 'resolveSpotifyPlaylistTracks' }

## Cause racine (vérification complète)
1. **Faux positif oauthScopes** : à l’OAuth initial, `tokens.scope || SPOTIFY_SCOPES`
   enregistrait tous les scopes même non accordés → probe DB OK, API /tracks 403.
2. **Probe session incomplet** : `/me` + scopes stockés suffisaient ; `/me/playlists`
   peut réussir sans accès réel aux morceaux (`/playlists/{id}/tracks`).
3. **403 bare Forbidden mal classé** : si scopes DB « OK », renvoyait `spotify_token_expired`
   au lieu de `spotify_scope_missing` → message trompeur, retry inutile.
4. **Scopes playlist partiels** : un seul scope (private OU collaborative) suffisait ;
   playlists mixtes → 403 selon le type choisi.
5. **Duplication frontend** : CreateSalonSpotifyPlaylistPicker et SalonSpotifyPlaylist
   dupliquaient chargement session, codes reconnect, mapping erreurs, retry load-playlist.
6. **Salon créé avant échec load** : pas de pré-vol → salon vide si load-playlist échoue.

## Correctif structurel

### Backend — modules partagés
- `spotifySession.ts` : codes auth, `spotifySessionFailureMessage()`, `respondSpotifySessionAuthFailure()`
- `spotifyPlaylistErrors.ts` : `SpotifyPlaylistError`, `throwSpotifyPlaylistApiError()`
- `spotifyPlaylists.ts` : refactoré (format propre), probe live `/tracks?limit=1`,
  `verifySpotifyPlaylistTrackAccess()`, invalidation scopes sur 403 bare
- `spotifyOAuth.ts` : plus de fallback `SPOTIFY_SCOPES` ; les deux scopes playlist requis ;
  `invalidateStoredSpotifyOAuthScopes()`
- Route `POST /platforms/spotify/playlists/verify-access` (pré-vol avant création)
- Routes `load-playlist`, `POST /salons`, `verify-access` : réponses auth unifiées

### Frontend — source de vérité
- `lib/spotifyPlaylistSession.ts` : codes reconnect, i18n, `toSpotifyPlaylistRef()`,
  `translateSpotifyApiError()`, `translateSalonCreateError()`
- `hooks/useSpotifyPlaylistLibrary.ts` : bibliothèque + session + verify + reconnect
- `components/SpotifyPlaylistPickerFields.tsx` : UI partagée (select, URL, erreur, reconnect)
- `CreateSalonSpotifyPlaylistPicker`, `SalonSpotifyPlaylist` : utilisent hook + champs partagés
- `CreateSalonModal` : verify-access **avant** createSalon ; plus de retry load-playlist inutile

Fin MODIF 479 - 2026-06-13
================================================================================

Date : 2026-06-13

## Symptôme
Après MODIF 477 : toast **« Impossible de charger la playlist — Forbidden »**
au chargement/sélection playlist (CreateSalonModal ou SalonPage).

## Cause racine
1. Spotify renvoie souvent 403 avec message brut `Forbidden` (pas
   « insufficient client scope ») sur `GET /playlists/{id}/tracks`.
2. MODIF 477 a correctement cessé de classer ce 403 en `spotify_token_expired`,
   mais `throwPlaylistApiError` affichait encore le détail brut dans le toast.
3. Comptes liés **avant** l'ajout des scopes playlist (`playlist-read-private`,
   `playlist-read-collaborative`) : `oauthScopes` vide ou incomplet →
   `probeSpotifyHostSession` laissait passer (garde `if (storedScopes && …)`),
   `/me/playlists` pouvait lister, `/tracks` échouait en 403 Forbidden.
4. `userNeedsSpotifyScopeReconnect` ne vérifiait pas les scopes playlist.

## Correctif
### Backend
- `isSpotifyBareForbiddenError` : détecte 403 sans détail explicite.
- `getMissingSpotifyPlaylistReadScopes` : scopes manquants si `oauthScopes` vide.
- `probeSpotifyHostSession` : échec `spotify_scope_missing` si scopes absents
  ou playlist-read manquants ; 403 bare → scope_missing.
- `resolveSpotifyPlaylistTracks` : pré-vol scopes + mapping 403 Forbidden
  → `spotify_scope_missing` (scopes manquants) ou `spotify_token_expired`
  (après refresh) ; plus de suffixe brut « Forbidden ».
- `spotifyFetch` : pas de retry refresh si scopes playlist manquants.
- `userNeedsSpotifyScopeReconnect` : inclut scopes playlist.

### Frontend
- Messages FR dédiés playlist (`errorPlaylistScopeMissing`, `errorPlaylistForbidden`).
- Retry load-playlist sur `spotify_scope_missing` / `spotify_playlist_forbidden`.
- Bouton reconnecter sur `spotify_playlist_forbidden`.
