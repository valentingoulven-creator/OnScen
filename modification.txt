2. POINTS CORRIGÉS
────────────────────────────────────────────────────────────────────────────────

CORRECTION 1 — Attribution YouTube sur les résultats de recherche
  Fichier : app/src/components/SalonYouTubeSearch.tsx
  Problème : Les résultats individuels de recherche YouTube n'affichaient
    aucune attribution/logo YouTube visible sur les miniatures.
    Seul le label général "Recherche YouTube" était présent en bas.
  Fix : Ajout d'un badge rouge "YouTube" en superposition sur chaque miniature
    de résultat de recherche.
    → Conformité : YouTube API Branding Guidelines (attribution visible requise)

CORRECTION 2 — Attribution YouTube sur le composant "Playlist hôte"
  Fichier : app/src/components/SalonYouTubePlaylist.tsx
  Problème : L'en-tête "Playlist hôte" ne mentionnait pas YouTube, pouvant
    prêter à confusion sur la source des playlists.
  Fix : Ajout d'un badge rouge "YouTube" inline dans l'en-tête du composant.
    → Conformité : YouTube API Branding Guidelines (source clairement identifiée)

CORRECTION 3 — Cache 1 heure sur la recherche YouTube (/youtube-search)
  Fichier : backend/src/routes/salons.ts
  Problème : La route GET /api/salons/youtube-search appelait l'API YouTube
    Data v3 à chaque requête, sans aucun cache. En production, cela consomme
    inutilement le quota API et ne respecte pas les bonnes pratiques de
    performance (quota journalier YouTube Data API = 10 000 unités).
  Fix : Cache en mémoire par requête (clé = query normalisée), TTL 1 heure.
    → Conformité : TTL << 24h (limite maximale ToS YouTube)
    → Bonus : réduction de la consommation de quota API YouTube Data v3
    → En-tête Cache-Control: private, max-age=3600 sur les réponses

CORRECTION 4 — Lien YouTube API Branding Guidelines dans les documents légaux
  Fichier : app/src/content/legal/apiPlatforms.ts
  Problème : La section 3 "YouTube / Google — API Services" référençait les
    CGU YouTube et Google, mais ne mentionnait pas les YouTube API Services
    Terms of Service ni les YouTube API Branding Guidelines (documents distincts
    des CGU utilisateur).
  Fix : Ajout dans la liste des documents de référence :
    • YouTube API Services Terms of Service
    • YouTube API Branding Guidelines
  Et ajout dans les exigences clés :
    • Ne pas stocker les données API YouTube > 24h (cache 1h appliqué)
    • Ne pas contourner le player officiel IFrame API
    • Ne pas permettre l'audio-only sans vidéo en production

OPTIMISATIONS PERFORMANCES & SCALABILITÉ — Soundly Dev

OBJECTIF
--------
  Préparer l'application à supporter 500 000 utilisateurs simultanés sans
  latence perceptible. Les optimisations sont de deux natures :
  (A) implémentées immédiatement (compatible msdev), et
  (B) documentées pour la production (nécessitent une infra dédiée).

────────────────────────────────────────────────────────────────────────────────
A. OPTIMISATIONS IMPLÉMENTÉES MAINTENANT
────────────────────────────────────────────────────────────────────────────────

1. Code splitting (React.lazy) — Frontend
   ─────────────────────────────────────
   Les pages les plus lourdes sont maintenant chargées à la demande :
   • ActualiteTabPage  (48 kB gzip)
   • DmPage            (41 kB gzip)
   • LivePage          (27 kB gzip)
   • SalonPage         (9 kB gzip)
   • UserProfilePage   (10 kB gzip)

   Chaque import statique a été remplacé par React.lazy() + Suspense.
   Un composant <PageFallback> (spinner minimaliste) s'affiche pendant
   le chargement.

   RÉSULTAT BUILD :
   • Bundle principal : 942 kB → 395 kB (−58 %)
   • GlobeView : 516 kB → 6.76 kB (chunk séparé déjà lazy)

2. Chunks Vite manuels — vite.config.ts
   ────────────────────────────────────
   rollupOptions.output.manualChunks divise les dépendances en :
   • vendor-react      (178 kB) — react, react-dom
   • vendor-socketio   (12 kB)  — socket.io-client
   • vendor-map        (182 kB) — leaflet, react-leaflet
   • vendor-three      — Three.js / @react-three (si présents)
   • vendor-misc       — autres node_modules

   Les vendors sont mis en cache navigateur indépendamment du code
   applicatif → rechargement partiel à chaque déploiement.

3. React.memo — Composants de liste
   ──────────────────────────────────
   • NearbyPeoplePanel : chaque ligne extraite en <NearbyPersonRow>
     mémorisée avec React.memo — ne se re-rend que si ses props changent.
     Impact : liste de 300 bots, aucun re-render inutile sur le parent.
   • ActualiteTabPage : <PostCard> mémorisé — un like ou un commentaire
     ne re-rend plus TOUTE la liste de publications.

4. loading="lazy" sur les images — Frontend
   ──────────────────────────────────────────
   Ajout de l'attribut loading="lazy" sur :
   • Avatars des posts (PostCard author + reshare)
   • Images attachées aux publications
   • FeaturedCard / NewsCard (actualités musicales)

   Le navigateur ne charge les images hors-viewport qu'au moment du scroll.

5. Socket.IO perMessageDeflate + httpCompression — bootstrap.ts
   ─────────────────────────────────────────────────────────────
   new Server(httpServer, {
     perMessageDeflate: { threshold: 1024 },
     httpCompression:   { threshold: 1024 },
   })
   Les messages WebSocket ≥ 1 Ko sont compressés. Réduction de la bande
   passante significative pour les événements salon_message, salon_updated, etc.

6. Cache API /api/news — routes/news.ts
   ──────────────────────────────────────
   Cache en mémoire, TTL 60 secondes.
   En-tête : Cache-Control: public, max-age=60
   Les 60 secondes suivant le premier appel sont servies instantanément
   sans reconstruire les items. buildItems() n'est appelé qu'une fois/min.

7. Cache API /api/auth/profile/:id — routes/auth.ts
   ──────────────────────────────────────────────────
   Cache par paire (userId cible, userId viewer), TTL 30 secondes.
   En-tête : Cache-Control: private, max-age=30
   Invalidation automatique lors d'un PATCH /api/auth/profile.
   Supprime la lecture DB répétée sur les profils fréquemment consultés.

8. Debounce geo/update — routes/geo.ts
   ─────────────────────────────────────
   Limite les mises à jour GPS à 1 toutes les 4 secondes par utilisateur.
   Les appels plus fréquents retournent instantanément les coordonnées
   brouillées existantes (sans écriture DB ni recalcul).

SYMPTÔME
--------
Après avoir choisi une couleur (Wave Soundly ou couleur unie) dans Profil →
Modifier, la couleur du pseudo ne se mettait pas à jour à l'écran.

CAUSE RACINE (2 bugs combinés)
------------------------------

1. JSON omet les champs `undefined` → état React jamais mis à jour pour la
   suppression de couleur
   ─────────────────────────────────────────────────────────────────────────
   Dans `backend/src/lib/profile.ts`, la fonction `publicProfile` retournait
   `usernameColor: snapshot.usernameColor` (et idem pour `usernameWaveFrom` /
   `usernameWaveTo`). Quand la couleur était effacée (supprimée côté serveur),
   la valeur était `undefined` → JSON.stringify omet le champ → la réponse
   API ne contient pas la clé `usernameColor`.

   Dans `AuthContext.tsx`, `setUserFromProfile` fait `{ ...prev, ...u }`. Si
   `u` ne contient pas la clé `usernameColor` (absente du JSON), le spread NE
   remplace PAS `prev.usernameColor`. L'ancienne couleur restait donc dans
   l'état React même après la sauvegarde. L'utilisateur voyait encore l'ancienne
   couleur après avoir sélectionné "Par défaut".

   FIX :
   • `backend/src/lib/profile.ts` → `usernameColor: snapshot.usernameColor ?? null`
     (idem pour `usernameWaveFrom` et `usernameWaveTo`). Le JSON inclut désormais
     `null` quand le champ est effacé, ce qui permet au spread côté frontend de
     l'écraser correctement.
   • `app/src/context/AuthContext.tsx` → `setUserFromProfile` détecte `=== null`
     et convertit en `undefined` (conforme au type `User`) avant de retourner le
     nouvel état.

2. Aucun aperçu du pseudo dans le formulaire d'édition
   ─────────────────────────────────────────────────────────────────────────
   Le seul `UsernameDisplay` de la page Profil était dans l'en-tête, en haut
   de la page. Quand l'utilisateur scrollait vers le bas pour accéder au
   `UsernameColorPicker`, l'aperçu disparaissait du champ visuel. Après la
   sauvegarde, la page ne scrollait pas vers le haut → l'utilisateur ne voyait
   pas que la couleur avait bien changé.

   FIX :
   • `app/src/pages/ProfilePage.tsx` → ajout d'un bloc "Aperçu du pseudo" avec
     un `UsernameDisplay` directement sous le `UsernameColorPicker` dans le
     formulaire d'édition. L'aperçu se met à jour en temps réel à chaque
     sélection de couleur, visible immédiatement sans scroll.

  app/src/context/AuthContext.tsx      → setUserFromProfile : gestion null → undefined
